## 1. Условие задачи

В приёмном отделении больницы работают два дежурных врача. Поступивший
пациент сначала проходит первичный осмотр, сообщает жалобы и получает
направление к стоматологу, хирургу или терапевту. После этого пациент
переходит в очередь соответствующего специалиста.

Каждый врач принимает только одного пациента. Пациенты не покидают очередь
самовольно. Продолжительность первичного осмотра и лечения задаётся случайно.
Срочные пациенты могут обслуживаться с приоритетом, но выбранная политика
не должна оставлять остальных пациентов без обслуживания.

### Инварианты

- один врач принимает не более одного пациента;
- пациент одновременно находится не более чем в одной очереди или у одного врача;
- направление выдаётся только после первичного осмотра;
- лечение выполняет специалист соответствующего профиля;
- пациент выписывается после завершения назначенного лечения.

### Завершение

Моделирование завершается после окончания приёма новых пациентов и
обслуживания всех поступивших или по прерыванию пользователем.

## 2. Сценарий: отображение сущностей в программы, процессы и потоки

### Разделение на сетевые приложения

| Программа | Роль | Отображаемая информация |
|-----------|------|-------------------------|
| `hospital_server` | Хранитель состояния модели, арбитр инвариантов | Только собственные события обработки запросов |
| `hospital_doctor` | Врач (дежурный или специалист) | Только собственные назначения и завершения |
| `hospital_patient` | Пациент | Только собственный жизненный цикл |
| `hospital_monitor` | Наблюдатель | **Комплексная картина** всей системы |

Такое разделение целесообразно: сервер — единственный владелец разделяемого
состояния (очереди, занятость врачей), что позволяет гарантировать инварианты
при произвольном числе независимых сетевых клиентов.

### Внутренняя структура сервера

- **Главный поток** — цикл `select()` на слушающем сокете с таймаутом 200 мс,
  что позволяет реагировать на флаг завершения без блокировки.
- **Поток на каждого клиента** (`pthread_create` + `pthread_detach`) —
  обслуживает протокол конкретной роли.
- **Поток снимков** — каждые 500 мс рассылает мониторам агрегированное
  состояние `SNAPSHOT`.
- Все разделяемые данные защищены мьютексом `state_mtx`; запись в сокет
  пациента дополнительно защищена персональным `send_mtx`, так как в него
  пишут разные потоки (поток врача и поток пациента).

### Конечный автомат пациента на сервере

```
P_FREE → P_WAIT_PRIM → P_IN_EXAM → P_WAIT_SPEC → P_IN_TREAT → P_DONE
                ↓            ↓            ↓             ↓
             P_ABORT     P_ABORT      P_ABORT       P_ABORT   (отключение клиента)
```

### Протокол обмена (текстовый, построчный)

**Клиент → сервер**

| Сообщение | Смысл |
|-----------|-------|
| `HELLO PATIENT` | регистрация пациента |
| `HELLO DOCTOR DUTY <num>` | регистрация дежурного врача |
| `HELLO DOCTOR SPEC <type> <num>` | регистрация специалиста |
| `HELLO MONITOR` | регистрация наблюдателя |
| `ARRIVE <urgent> <exam_ms> <treat_ms>` | поступление пациента |
| `READY` | врач готов принять пациента |
| `EXAM_DONE <pid>` | первичный осмотр завершён |
| `TREAT_DONE <pid>` | лечение завершено |
| `BYE` | корректное отключение |

**Сервер → клиент**

| Сообщение | Смысл |
|-----------|-------|
| `WELCOME <role> <id>` | подтверждение регистрации |
| `QUEUED <pos>` | пациент поставлен в очередь |
| `ASSIGN_EXAM <pid> <ms> <urgent>` | назначение дежурному врачу |
| `ASSIGN_TREAT <pid> <ms>` | назначение специалисту |
| `WAIT` / `WAIT busy` | нет работы / слот занят |
| `REFERRAL <spec>` | направление пациенту |
| `DISCHARGED` | выписка |
| `EVENT <текст>` | событие для монитора |
| `SNAPSHOT <поля>` | агрегированное состояние для монитора |
| `SHUTDOWN server_stopping` | сервер завершает работу |
| `REJECT <причина>` | отказ в регистрации |

### Соблюдение инвариантов

| Инвариант | Механизм |
|-----------|----------|
| Один врач — один пациент | поле `busy_pid` в слоте врача; при `READY` занятый слот получает `WAIT busy` |
| Пациент в одном месте | единственное поле `st` (конечный автомат), все переходы под `state_mtx` |
| Направление после осмотра | `REFERRAL` отправляется только в обработчике `EXAM_DONE` |
| Профиль специалиста | пациент попадает в `q_spec[p->spec]`, слот специалиста привязан к `type` |
| Выписка после лечения | `DISCHARGED` отправляется только в обработчике `TREAT_DONE` |
| Приоритет срочных без голодания | срочные вставляются в начало первичной очереди; их доля ограничена (~20 %), обычные пациенты обслуживаются FIFO |

## 3. Пользовательский интерфейс

Каждая программа ведёт независимый вывод с временными метками вида `[  1.234]`,
реализованный **системным вызовом `write()`** в `STDOUT_FILENO` и в собственный
файл-журнал (дескриптор получен через `open()`).

- **Сервер** — события обработки запросов + итоговая статистика.
- **Врач** — «НАЧАЛ ОСМОТР / ЗАВЕРШИЛ ОСМОТР», «НАЧАЛ ЛЕЧЕНИЕ / ЗАВЕРШИЛ ЛЕЧЕНИЕ».
- **Пациент** — поступление, позиция в очереди, направление, выписка.
- **Монитор** — поток событий **и текстовая панель состояния**:

```
+------------------ СОСТОЯНИЕ БОЛЬНИЦЫ ------------------+
 Очередь к дежурным : 3      Стоматолог: 1
 Хирург             : 0      Терапевт  : 2
 Дежурные врачи     : 0:busy,1:busy
 Специалисты        : Стоматолог0:busy,Хирург0:free,Терапевт0:busy
 Прибыло: 8     Выписано: 4     Отказов: 0     План: 12
+-------------------------------------------------------+
```

Журналы: `hospital_server.log`, `doctor_<роль><тип>_<номер>.log`,
`patient.log`, `monitor.log`.

## 4. Варианты запуска и завершения

### Компиляция

```bash
gcc -std=c99 -Wall -o hospital_server  hospital_server.c  -lpthread
gcc -std=c99 -Wall -o hospital_doctor  hospital_doctor.c  -lpthread
gcc -std=c99 -Wall -o hospital_patient hospital_patient.c -lpthread
gcc -std=c99 -Wall -o hospital_monitor hospital_monitor.c -lpthread
```

Библиотека `-lrt` не требуется: используются только сокеты Беркли и pthread.
Программы собираются и работают как на Linux, так и на macOS.

### Параметры командной строки

**Сервер**

| Параметр | Описание | По умолчанию |
|----------|----------|--------------|
| `--port N` | TCP-порт | 5555 |
| `--patients N` | целевое число пациентов | 12 |
| `--duty N` | число дежурных врачей (1..8) | 2 |
| `--per-spec N` | специалистов на профиль (1..4) | 1 |
| `--seed S` | зерно ГСЧ (распределение заболеваний) | 42 |

**Врач:** `--host`, `--port`, `--role duty|spec`, `--type 0..2`, `--num N`, `--reconnect`

**Пациент:** `--host`, `--port`, `--urgent 0|1`, `--exam ms`, `--treat ms`, `--seed S`

**Монитор:** `--host`, `--port`, `--reconnect`, `--quiet`

IP-адрес и порт задаются в командной строке у **всех** клиентов, что обеспечивает
работу как на одном компьютере, так и в распределённом режиме.

### Локальный запуск

```bash
./hospital_server --port 5555 --patients 12 --duty 2 --seed 42

./hospital_doctor --host 127.0.0.1 --port 5555 --role duty --num 0 --reconnect
./hospital_doctor --host 127.0.0.1 --port 5555 --role duty --num 1 --reconnect
./hospital_doctor --host 127.0.0.1 --port 5555 --role spec --type 0 --num 0 --reconnect
./hospital_doctor --host 127.0.0.1 --port 5555 --role spec --type 1 --num 0 --reconnect
./hospital_doctor --host 127.0.0.1 --port 5555 --role spec --type 2 --num 0 --reconnect

./hospital_monitor --host 127.0.0.1 --port 5555 --reconnect

./hospital_patient --host 127.0.0.1 --port 5555 --seed 101
```

### Распределённый запуск (несколько компьютеров)

```bash
# Машина A (192.168.1.10) — сервер
./hospital_server --port 5555 --patients 30

# Машина B — дежурные врачи
./hospital_doctor --host 192.168.1.10 --port 5555 --role duty --num 0 --reconnect

# Машина C — специалисты
./hospital_doctor --host 192.168.1.10 --port 5555 --role spec --type 1 --num 0 --reconnect

# Машины D, E, F — независимые наблюдатели
./hospital_monitor --host 192.168.1.10 --port 5555 --reconnect

# Машина G — пациенты
./hospital_patient --host 192.168.1.10 --port 5555 --seed 55
```

Сервер привязывается к `INADDR_ANY`, поэтому доступен из сети без изменений кода.

### Варианты завершения

1. **Штатное завершение модели.** Когда `arrived >= target` и
   `discharged + aborted >= arrived`, сервер снимает флаг `running`,
   рассылает `SHUTDOWN` всем клиентам, ждёт 300 мс, пишет статистику и выходит.
2. **Прерывание оператором (`Ctrl+C` / `SIGINT`).** Обработчик сигнала
   устанавливает `running = 0`; далее выполняется тот же корректный путь
   завершения с рассылкой `SHUTDOWN`.
3. **Отключение клиента-врача.** Слот помечается offline, незавершённый
   пациент возвращается **в начало** соответствующей очереди. Сервер
   продолжает работу; врач может переподключиться (`--reconnect`).
4. **Отключение клиента-пациента.** Пациент удаляется из очереди либо
   помечается `P_ABORT` и учитывается в статистике как незавершённый.
5. **Отключение клиента-монитора.** Слот освобождается, рассылка продолжается
   остальным мониторам; ошибка записи приводит к `shutdown()` сокета,
   что пробуждает поток монитора для очистки слота.

## 6. Реализация требований по уровням оценки

| Уровень | Требование | Где реализовано |
|---------|-----------|-----------------|
| 4-5 | Сервер и клиенты, независимый локальный вывод | `hospital_server.c`, `hospital_doctor.c`, `hospital_patient.c` |
| 4-5 | IP и порт в командной строке | `--host`, `--port` у всех клиентов, `--port` у сервера |
| 4-5 | Работа на одном ПК и в сети | `INADDR_ANY` на сервере, `getaddrinfo` на клиентах |
| 6-7 | Отдельный клиент комплексного отображения | `hospital_monitor.c`, сообщения `EVENT` + `SNAPSHOT` |
| 8 | Множество мониторов, динамика | массив `monitors[32]`, `broadcast_event`, очистка слота при ошибке записи |
| >8 | Отключение/переподключение рабочих клиентов | `--reconnect`, возврат пациента в очередь в `serve_doctor` |
| >8 | Завершение всех клиентов при остановке сервера | `shutdown_all_clients()`, сообщение `SHUTDOWN` |

| № | Требование | Реализация |
|---|-----------|------------|
| 1 | Комментарии | Все файлы прокомментированы: назначение структур, протокола, логики |
| 2 | Системные вызовы и дескрипторы | `socket`, `bind`, `listen`, `accept`, `connect`, `read`, `write`, `open`, `close`, `select`, `shutdown` |
| 3 | Тестовые наборы и скрипты | `run_tests.sh` — 5 сценариев, включая аварийные |
| 4 | Промпты ИИ | раздел 7 |
| 5 | Критическая оценка ИИ-кода | раздел 7 |
| 6 | Непредусмотренные решения | текстовый протокол (отладка через `nc`), панель состояния, `--seed`, `TCP_NODELAY`, журнал на каждый клиент |

### Непредусмотренные решения, повышающие качество

1. **Текстовый построчный протокол.** Систему можно наблюдать без
   специально скомпилированного клиента:
   ```bash
   printf 'HELLO MONITOR\n' | nc 127.0.0.1 5555
   ```
   Это одновременно упрощает отладку и демонстрирует работу множества
   независимых наблюдателей.
2. **`TCP_NODELAY`** на всех соединениях — отключает алгоритм Нейгла,
   убирая задержки до 40 мс на коротких сообщениях протокола.
3. **Персональный мьютекс отправки** у каждого пациента — устраняет гонку
   при записи в один сокет из потока врача и потока пациента.
4. **`select()` с таймаутом** в цикле приёма подключений — позволяет
   реагировать на `SIGINT` без блокировки в `accept()`.

1. **Опечатка в форматной строке (исправлено).** В `hospital_patient.c`
   в сообщении о выписке была кириллическая буква `д` вместо спецификатора
   `%d`: `"Пациент %д ВЫПИСАН"`. Это приводило к некорректному выводу.
   Исправлено на `%d`.

2. **Гонка записи в сокет пациента (учтено в архитектуре).** Сообщения
   `REFERRAL` и `DISCHARGED` отправляются из потока врача, а `QUEUED` — из
   потока пациента. Без синхронизации строки могли бы перемешаться.
   Введён персональный `send_mtx` для каждого пациента.

3. **Блокировка `accept()` при завершении (учтено).** Прямой вызов
   `accept()` не позволил бы отреагировать на `SIGINT`. Заменён на
   `select()` с таймаутом 200 мс.

4. **`SIGPIPE` при отключении клиента (исправлено).** Запись в закрытый
   сокет по умолчанию убивает процесс сигналом `SIGPIPE`. Во всех
   программах установлен `signal(SIGPIPE, SIG_IGN)`, ошибки `write()`
   обрабатываются явно.

5. **Освобождение слота монитора при обрыве (исправлено).** Поток монитора
   блокируется на `read()` и не узнаёт об ошибке записи. Добавлен
   `shutdown(fd, SHUT_RDWR)` при неудачной отправке — это пробуждает
   `read()` и слот корректно освобождается.

6. **Потеря пациента при отключении врача (исправлено).** В исходном
   варианте пациент оставался в состоянии `P_IN_EXAM` навсегда. Добавлен
   возврат в начало очереди при освобождении слота врача, что и обеспечивает
   выполнение требования на оценку выше 8.
